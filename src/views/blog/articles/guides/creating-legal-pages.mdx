The app has two legal pages: **Privacy Policy** (`/privacy`) and **Cookies Notice** (`/cookies`). They are written in MDX, in English and Hebrew, edited in the MDX editor, and linked from the footer — but they are **not Blog articles**. They live in `src/views/blog/articles/app-pages/` and the build treats them specially.

## Why not Blog articles?

A Blog article is listed, routed and pre-rendered automatically — you drop in a file and it works. The legal pages need a few lines of code because the app links to them **by name** (a route, a footer link, a title in the i18n catalogs). They also must not appear in the Blog's index, its sidebar, its sitemap or the browser accessibility pass's Blog routes.

The folder `app-pages/` is **inside the Blog's articles folder** so the MDX editor lists, edits and saves its files — but `APP_PAGES_FOLDER` / `isAppPagePath` (in `src/lib/articleFrontmatter.ts`) keep it out of the Blog entirely: no index card, no sidebar entry, no `/blog/app-pages/…`, no Blog sitemap line.

## The operator placeholders — filled in at build time (CTA-182)

The repository is public. A fork must not publish chessapp.dev's operator as its own. So the documents say `%OPERATOR_NAME%`, `%OPERATOR_ADDRESS%` and `%PRIVACY_EMAIL%` where the details go, and the build puts them in from environment variables.

| Placeholder | Variable | Required | Hebrew value |
|-------------|----------|----------|--------------|
| `%OPERATOR_NAME%` | `SITE_OPERATOR_NAME` | yes | `SITE_OPERATOR_NAME_HE` |
| `%OPERATOR_ADDRESS%` | `SITE_OPERATOR_ADDRESS` | yes | `SITE_OPERATOR_ADDRESS_HE` |
| `%PRIVACY_EMAIL%` | `SITE_PRIVACY_EMAIL` | yes | — (one value for every language) |

A language's own value is `<VARIABLE>_<LANG>` (`_HE` for the `.he.mdx` files); unset, that language shows the English one, and a new language reads `_<ITS CODE>` the same way. The value is inserted as text — MDX's `{` and `<` are escaped — so Markdown in it (`*`, `_`) stays Markdown. An empty value, or one of only spaces, counts as unset.

The build reads them from the environment and from `.env` / `.env.local` — a variable set in the shell wins — and asks **one predicate**, `legalPagesConfigured` (`src/lib/siteOperator.ts`), which has three answers:

| The three required variables | The build |
|------------------------------|-----------|
| all set | has the legal pages, the placeholders filled |
| none set | **passes**, without the legal pages |
| some but not all | **fails**, naming the missing ones |

### All set — the build has the pages

`plugins/siteOperator.ts` (a Vite plugin with `enforce: "pre"`) fills the placeholders in every `.mdx` under `app-pages/` **before the MDX compiler reads it**, so the dev server, the browser bundle, the server bundle and the pre-render all compile the same text.

An unknown placeholder (e.g. `%OPERATOR_PHONE%`) fails the build, naming the file.

### None set — the build passes, without the pages

**Nothing fails without the variables.** A fork, a plain local run and `ci.yml`'s pull-request build all have none, and `yarn build`, `yarn check:pages`, `yarn check:blog-build` and the tests pass. The build **leaves the pages out entirely**: `__LEGAL_PAGES__` is `false` (read as `LEGAL_PAGES_SHOWN` in `src/views/legal/legalPagesShown.ts`), so:

- `src/routes.tsx` has no `/privacy` or `/cookies` route — hence no pre-rendered page, no sitemap line
- The footer has no links to them
- The Blog's manifest lists no file of `app-pages/`, so none of their text is in `dist/`
- The build logs a warning — `No site operator configured (SITE_OPERATOR_NAME, SITE_OPERATOR_ADDRESS, SITE_PRIVACY_EMAIL): no legal pages in this build`; a deploy shows it as a warning on the run

What that looks like on a machine: in `yarn dev`, `/privacy` and `/cookies` lead to the not-found page, and the footer has no legal links. The MDX editor still lists, opens and saves the two documents, but its lobby's link to each page leads to that same missing route. To see the pages, set the variables (below).

### Some but not all — the build fails

**Half-configured is an error**: the build stops with `The site's operator is half configured: SITE_PRIVACY_EMAIL is unset…`, naming every missing variable. A deploy that forgot one should not quietly lose its Privacy Policy. Set the missing ones, or clear all three to build without the pages.

The `_HE` variables are never required: setting one without the English three is still "none set".

## What the files look like

`src/views/blog/articles/app-pages/privacy.mdx`:

```mdx
---
title: "Privacy Policy"
summary: "What chessapp.dev keeps on your device, what it never collects, and your rights under the GDPR and Israel's Protection of Privacy Law."
---

Last updated: 11 October 2026

…

## Data controller

The App is operated by **%OPERATOR_NAME%**, %OPERATOR_ADDRESS%, who is the data controller for the processing this policy describes. For any privacy question or request, write to **%PRIVACY_EMAIL%**.

…
```

The Cookies Notice (`cookies.mdx`) follows the same pattern, its contact line at the foot:

```mdx
Questions: **%PRIVACY_EMAIL%** — %OPERATOR_NAME%, %OPERATOR_ADDRESS%.
```

Each has its Hebrew translation beside it (`privacy.he.mdx`, `cookies.he.mdx`), with the same placeholders.

## Editing the pages

Open the MDX editor (`yarn mdx-editor:start`, then `/dev/mdx-editor`). The lobby lists the `app-pages` folder — open Privacy Policy or Cookies Notice, edit, and **Save**. The editor reads `?raw`, which the plugin leaves alone, so it shows the placeholders (and its preview too) — **keep them** when editing the operator's paragraph.

Only the body is yours to change freely. Renaming a page (its `title` / `summary`) means changing `pages.<id>` / `pageDescriptions.<id>` in both catalogs (`src/locales/en.ts`, `src/locales/he.ts`) to the same words (and `footer.<id>` if the footer link should follow). The test fails until they match. When the page changes, update its "Last updated" line.

## Local development — seeing the filled pages

Copy the lines from `.env.example` into `.env.local` (gitignored) and fill them in:

```bash
SITE_OPERATOR_NAME="Your Name"
SITE_OPERATOR_NAME_HE="Your name in Hebrew"
SITE_OPERATOR_ADDRESS="Your Street, Your Town"
SITE_OPERATOR_ADDRESS_HE="Your address in Hebrew"
SITE_PRIVACY_EMAIL="privacy@example.org"
```

Fill the three required ones or none — copying `.env.example`'s empty lines as they are is "none set", and builds without the pages. Then restart `yarn dev` (the variables are read when it starts) or run `yarn build`. In a worktree, `.jst/bootstrap.sh` keeps every line of `.env.local` but its own port line, so your operator values persist across bootstrap runs.

## In CI and the deploys

The values are **repository variables** — not secrets: the pages publish them anyway, and a variable's value is readable in the run's log, which is fine here.

| Workflow | Builds |
|----------|--------|
| `build.yml` (both deploys: `build-gh.yml`, `build-swa.yml`) | with the variables — the deployed site has the pages |
| `a11y.yml` | with the variables — so the browser pass visits the pages |
| `ci.yml` (every pull request) | **without them, on purpose** — a fork's build, and its checks hold `dist/` to "no legal pages" |

Set them once per repository:

```bash
gh variable set SITE_OPERATOR_NAME --body "Your Name"
gh variable set SITE_OPERATOR_NAME_HE --body "Your name in Hebrew"
gh variable set SITE_OPERATOR_ADDRESS --body "Your Street, Your Town"
gh variable set SITE_OPERATOR_ADDRESS_HE --body "Your address in Hebrew"
gh variable set SITE_PRIVACY_EMAIL --body "privacy@example.org"
gh variable list                      # check
```

**Set them before a change that needs them reaches `main`**: a deploy without them publishes the site with no Privacy Policy, and says so only in a warning. After a deploy, check the live page names the operator:

```bash
curl -s https://chessapp.dev/privacy/ | grep -c "%OPERATOR_"   # 0
```

## Tests and verification

The build checks hold `dist/` to the build's own decision (`legalPagesShown`, exported by the server entry):

- `yarn check:pages` — the pages are there, or no page and no link to one
- `yarn check:blog-build` — with the pages, no placeholder left anywhere; without them, the Blog's manifest lists no file of `app-pages/` and none of their text ships
- The browser accessibility pass (`yarn test:a11y`) visits the two pages only when the build wrote them (`LEGAL_PAGES_BUILT`, `e2e/a11y/routes.ts`)

Under Vitest the build is configured with fixed values (`src/test/siteOperator.ts`), whatever the machine has — so the tests are the same everywhere, with or without your `.env.local`; `src/views/legal/legalPagesHidden.test.tsx` mocks `legalPagesShown.ts` for a build without them.

## Adding another in-app page

The steps are documented in [`docs/in-app-pages.md`](https://github.com/pgntools/chess-trainer-app/blob/main/docs/in-app-pages.md) — the same pieces, with a Terms of Use page (`/terms`) as the example:

1. Write the document in `app-pages/terms.mdx` (and `terms.he.mdx`)
2. Add catalog keys in both languages
3. Register the page id in `legalDocuments.ts`
4. Add a wrapper in `LegalMain.tsx` and the route in `routes.tsx` (inside the `LEGAL_PAGES_SHOWN` spread)
5. Update tests and the browser pass routes
6. Optionally, add a footer link in `Footer.tsx` (inside the `LEGAL_PAGES_SHOWN` fragment)
7. Run the check commands from Step 8 in that document

## What you do not need to do

- **No pre-render list**: `prerenderedPages()` takes every static route from the route table
- **No sitemap entry**: the pre-render writes one for every page it renders
- **No sidebar entry**: these pages are not in the sidebar
- **No Blog exclusion**: anything under `app-pages/` is left out of the Blog by its path
- **No share image**: the page falls back to the site's own (`src/assets/share/default.png`)

## Keeping the texts true

The Privacy Policy and the Cookies Notice make claims about the hosts, cookies, server logs, and the operator. What keeps those claims true as the code and the hosting change is documented in [`docs/privacy-policy-checks.md`](https://github.com/pgntools/chess-trainer-app/blob/main/docs/privacy-policy-checks.md) — the hosts' cookies, the Azure logging checks, and what to re-run after a plan upgrade, an API or a new host.
